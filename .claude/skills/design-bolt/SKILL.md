# 디자인 Bolt (디자인 작업의 1사이클)

디자이너의 1사이클을 진행한다. 대상은 인자로 지정된 화면이다. 일하는 방식의 전체상은 `docs/guidelines/designer-workflow.md`, 문서 작법의 심사 기준은 `design/DESIGN-CHARTER.md` 를 정본으로 한다.

## 페이즈 1: 계획 (승인까지 덮어쓰기 금지)

1. 다음을 읽는다.
   - 대상 화면의 `design/screens/<screen-id>/UI-SPEC.md` (있으면)
   - `design/DESIGN.md` (요소의 규칙) · `design/UX-PATTERNS.md` (횡단 패턴)
   - `design/DS-update-list.md` (디자인 시스템에 무엇이 있고 무엇이 없는가)
   - `design/docs/screen-inventory.md` (있으면)

   **요소의 규칙을 화면마다 재발명하지 않는다.**

2. **가드**: UI-SPEC의 **§1~5(UX 설계 의도)가 `UX승인` 상태가 아니면 정지**한다.
   - §1~5가 비어 있으면 **§1~5만 먼저 작성**하고 승인을 받는다. §6 이하로 내려가지 않는다.
   - 이것이 이 리포의 spec-first다. 별도 spec 파일은 두지 않는다.

3. 다음을 제시한다.
   - **구성 요소 목록** (English·PascalCase)
   - **상태 목록** (정상·로딩·빈 상태·에러의 4상태. 에러는 거동·대체 플로우 포함)
   - **레이아웃 방침** (화면 구조·반응형의 취급)
   - **디자인 시스템에서 부족한 것** — 있으면 `DS-nn` 기표 후보로 제시한다
   - **판단이 필요한 점** (선택지와 추천)
   - UI-SPEC의 애매한 점·모순 (있으면. 디자인으로 멋대로 메우지 않는다)

4. **재정을 기다린다.** 제시의 말미는 반드시 2택으로 한다: **「A) 수정을 의뢰한다 / B) 이 계획으로 진행한다」**. 애매한 재정(「알아서」 등)은 확정 정보로 삼지 않고, 추가 질문으로 해소한 뒤 진행한다.

## 페이즈 2: 실행 (승인된 계획이 유일한 진실)

- 착수 전에 승인된 계획을 체크박스로 UI-SPEC의 「실행 계획」 절에 써 넣는다. **각 단계 완료 직후에 [x]** 를 붙인다.

- `design/screens/<screen-id>/UI-SPEC.md` 의 **§6~11** 을 작성한다. 절 순서를 바꾸지 않는다.
  - **「적용 패턴」 절의 운용**
    - **판정 조건**: 쓰려는 UX 판단이 이미 `design/UX-PATTERNS.md` 에 있다 → **아크션**: `P-nn` 을 참조하고 다시 쓰지 않는다.
    - **판정 조건**: 같은 판단이 2화면째에 나타났다 → **아크션**: `UX-PATTERNS.md` 로 승격시킨다(헌장 원칙 7).
  - **「블록별 규칙」 절의 성격** — 그 화면에서만 성립하는 것만 쓴다. 다른 화면에서도 성립하는 판단은 `UX-PATTERNS.md` 로 빼고 여기서는 `P-nn` 참조만 한다.
  - 컴포넌트 레벨의 규칙(variant 계층 등)은 디자인 시스템을 따르고 UI-SPEC에 중복 기재하지 않는다.

- **HtmlTemplate은 Claude Design에서 만들어 취임한다.**
  1. **생성·익스포트(디자이너 조작)**: 승인된 §1~5와 §6~8을 프롬프트 소재로 삼는다. 디자이너가 claude.ai의 Claude Design에서 4상태를 만들고 익스포트한다.
     - **AI는 Claude Design을 조작할 수 없다.** 이 단계에서 디자이너 조작 대기로 정지하고 파일 수령을 기다린다.
  2. **배치**: 받은 익스포트를 `design/screens/<screen-id>/template/` 에 둔다.
  3. **`template/SOURCE.md` 를 만든다** (필수). 3줄이면 된다.
     ```
     - Claude Design: <공유 링크>
     - 생성일: <YYYY-MM-DD>
     - 대응 UI-SPEC: <커밋 해시 또는 버전>
     ```
     **없으면 나중에 템플릿과 UI-SPEC의 정합을 판정할 수 없다.**

- **template 취급의 판정 조건**:

  `template/` 은 **인계 산출물**이다([ADR-0005](../../../docs/adr/0005-design-team-deliverables.md)). 엔지니어가 열어서 바로 보는 것이므로 형태를 고정한다.

  | 판정 조건 | 아크션 |
  |---|---|
  | 익스포트에 JS·인라인 이벤트가 들어 있다 | **지운다.** 정적 HTML/CSS 만 남긴다. 인터랙션 의도는 UI-SPEC §8 이 갖는다 |
  | 4상태가 한 파일에 토글로 들어 있다 | **상태마다 1파일로 가른다.** 최종 형태는 **4파일**(`normal` · `loading` · `empty` · `error`) |
  | 반응형 3구간을 어떻게 담는가 | **CSS 가 처리한다.** 구간마다 파일을 늘리지 않는다. 4파일 × 3구간 ＝ 12파일은 유지되지 않는다 |
  | 필요한 수정이 문언·스타일 조정 범위다 | Claude Code로 직접 고쳐도 된다(UI-SPEC과의 정합을 유지한다) |
  | 레이아웃·구조 레벨의 변경이 필요하다 | Claude Design으로 돌아가 재생성·재익스포트한다 |

  **JS 를 남기면 어느 상태가 정본인지 판정할 수 없다.** 토글로 가려진 것은 엔지니어가 못 본다.

- ⚠️ **`template/` 은 React 구현의 「시각적 참조」이지 「코드 이식원」이 아니다.**
  - **CSS를 그대로 옮기지 않는다.** 구현은 디자인 시스템의 토큰과 컴포넌트로 한다.
  - 이것을 어기면 토큰 체계가 두 갈래로 갈라진다. **이 리포에서 가장 지키기 어렵고 가장 중요한 한 줄이다.**

- 계획에 없는 화면·요소를 추가하지 않는다. API가 미정의라고 판명되면 정지하고 백엔드 담당과의 합의를 먼저 제안한다.

## 페이즈 3: 자기검증·클로즈

1. **6품질축 감사**: frontend-design 플러그인을 쓸 수 있으면 그 리뷰 기능으로 감사한다. 없으면 아래 내장 체크리스트로 수동 감사한다. **전 상태를 대상으로 한다.**

2. **표시 확인**: playwright를 쓸 수 있으면 브라우저 조작·스크린샷으로 확인한다.
   - 없으면 `chromium --headless --screenshot=<출력> --window-size=<폭>,<높이> <대상>` 으로 4상태를 촬영한다.
   - ⚠️ **headless Chromium은 창 최소 폭 500px를 강제한다.** 그 미만을 지정하면 레이아웃은 500px인 채 스크린샷만 잘린다.
   - 그래서 **가짜 넘침이 된다.** 375px 확인은 playwright나 실제 브라우저의 DevTools로 한다.

3. 감사·확인 결과를 `design/screens/<screen-id>/UI-REVIEW.md` 에 기록한다. 지적이 0건이어도 그 취지를 쓴다.

4. **디자인 시스템에 부족한 것을 `DS-update-list.md` 에 기표한다.** 화면에서 즉석으로 만들지 않는다. 기표하면 `DS-nn` 이 붙는다.

5. 수용 조건과 UI-SPEC의 상태를 대조해 갱신한다.

6. **기표자 리뷰를 안내한다.** PR은 **Draft로 만들고, CI 실행 후에 이 세션과는 다른 세션에서 `/pr-review` 를 자기 Draft PR에 1회 통과시킨 뒤 Ready로** 한다.
   - **이 세션에서 그 리뷰를 실행하지 않는다.** 디자인한 문맥 그대로는 다른 눈이 되지 않는다.
   - 이 리포는 구현자가 Claude 하나이므로 **세션 분리가 유일한 견제 장치다.**

7. 검증 결과를 있는 그대로 보고한다(실패를 얼버무리지 않는다). 커밋 메시지 안을 제시한다. push·PR 작성은 사람의 지시를 기다린다.

8. 보고의 말미는 반드시 2택: **「A) 수정을 의뢰한다 / B) 승인하고 클로즈」**.

## 내장: 6품질축 체크리스트

| 축 | 확인할 것 |
|---|---|
| 레이아웃 | 여백·정렬이 일관된다. 주요 요소의 시선 순서가 목적에 맞는다 |
| 컬러 | 사용색이 한정되어 있다. 의미색(에러＝빨강 등)이 일관된다 |
| 타이포그래피 | 제목·본문의 크기 계층이 일관된다. 폰트 지정이 전 페이지 동일하다 |
| 인터랙션 | 링크·버튼에 hover / focus 스타일이 있다. 누를 수 있는 것과 없는 것이 구분된다 |
| 접근성 | 아래 「접근성 축」을 쓴다 |
| 반응형 | 폭을 좁혀도 가로 스크롤·요소 붕괴가 없다(최소 375px / 768px / 1280px) |

### 접근성 축 — 집행층으로 가른다

기준선은 **WCAG 2.1 AA**로 둔다.

**이 리포에 a11y 자동 검사가 없다**([ADR-0005](../../../docs/adr/0005-design-team-deliverables.md)). 헌장 원칙 5에 따라 **블로커를 세우지 않는다.** 전부 기록하고 넘긴다.

| 판정 조건 | 아크션 |
|---|---|
| 대비·포커스 표시·타겟 사이즈의 미달을 발견했다 | **`DS-nn` 으로 기표한다.** 토큰·컴포넌트 층에서 한 번 정하면 전 화면에 먹으므로 화면에서 고치지 않는다 |
| 사람이 판정하는 항목의 미달을 발견했다(아래 표) | **`UI-REVIEW.md` 에 기록하고 넘긴다.** 클로즈를 막지 않는다 |
| 발견한 것이 하나도 없다 | **`UI-REVIEW.md` 에 「0건」이라고 적는다.** 안 봤는지 없는지를 구별할 수 있게 한다 |

**사람이 판정하는 항목** — 기계가 못 잡으므로 눈으로 본다.

| 확인할 것 | 달성 기준 |
|---|---|
| 이미지·아이콘에 의미에 맞는 `alt` (장식이면 `alt=""`) | 1.1.1 |
| 정보를 색만으로 전달하지 않는다 | 1.4.1 |
| 포커스 순서가 시각적 배열과 일치한다 | 2.4.3 |
| 제목 레벨이 건너뛰지 않는다. 제목과 라벨이 내용을 나타낸다 | 1.3.1 / 2.4.6 |
| 폼 요소에 `label` (플레이스홀더로 대신하지 않는다). 에러는 무엇이 문제인지 문언으로 보여준다 | 3.3.1 / 3.3.2 |
| 페이지에 `lang` 이 있다. 페이지 제목이 내용을 나타낸다 | 3.1.1 / 2.4.2 |

**자동 검사만으로 합격 판정하지 않는다.** 대체 텍스트의 **내용**의 타당성, 포커스 순서의 의미적 올바름, 제목 구조의 타당성은 기계 판정할 수 없다.

## 금지 사항

- §1~5가 승인되지 않은 채로 §6 이하를 쓰는 것
- `template/` 의 CSS를 React 구현으로 그대로 옮기는 것
- `template/SOURCE.md` 없이 템플릿을 커밋하는 것
- UI-SPEC과 모순되는 템플릿을 남기는 것 (**UI-SPEC이 항상 정본**. 어긋나면 양쪽을 고친다)
- 디자인 시스템에 없는 요소를 화면에서 즉석으로 만드는 것 (`DS-nn` 으로 기표한다)
