# PR Review (PR의 해설과 리뷰)

**이 리포에서 이 스킬은 유일한 견제 장치다.** 구현자가 Claude 하나이므로, 사람 둘의 상호 견제가 없다.

- **구현한 세션에서 이 스킬을 돌리지 않는다.** 같은 문맥으로는 다른 눈이 되지 않는다.
- **approve·merge·수정 push 를 하지 않는다.** 지적까지가 이 스킬의 일이다.

## 손순서

### 1. 대상 PR을 특정한다

인자가 없으면 열린 PR을 나열하고 사람에게 고르게 한다. 마음대로 고르지 않는다.

### 2. 입력을 모은다

깊이와 범위를 먼저 정한다. **차분 전체를 읽지 않고 리뷰를 시작하지 않는다.**

| 모으는 것 | 경로 |
|---|---|
| 차분 | `pull_request_read` (get_diff) |
| PR 본문 | **`search_pull_requests` 의 `body`**. `pull_request_read` 는 가공판을 돌려주므로 본문의 실체로 쓰지 않는다 |
| CI 결과 | `get_check_runs`. **`curl` 로 가져오지 않는다** |
| 기존 지적 | `get_review_comments` (재리뷰일 때) |

**기다리기 전에 기본 브랜치와의 충돌을 확인한다.** 충돌한 PR은 체크가 만들어지지 않아 기다려도 오지 않는다.

### 3. 해설을 만든다

차분이 무엇을 바꾸는지 비개발자도 읽을 수 있게 쓴다. 디자이너가 읽는다.

### 4. 관점을 갈라서 리뷰한다

차분의 경로로 관점을 바꾼다. **해당하지 않는 관점을 헛돌리지 않는다.**

| 차분의 경로 | 관점 |
|---|---|
| `design/**`·`docs/**` | `CLAUDE.md` 상설 지시와의 정합 ／ **[한국어 규약](../../../docs/guidelines/korean-writing-rules.md) 의 R1·R2·R5·R7~R9**(결론을 먼저·두 값·미확정·군더더기·제목과 문단·말의 고르기) ／ **차분과 PR 본문 양쪽**에 적용한다 ／ `DESIGN-CHARTER.md` 8원칙 테스트 ／ UI-SPEC과 template의 어긋남 ／ `DS-nn` 의 상태와 실물의 어긋남 |
| `design/ds-export/**` | **손으로 고친 흔적이 없는가**(교체는 통째로 한다) ／ `SOURCE.md` 의 SHA-256 을 갱신했는가 ／ 늘거나 준 컴포넌트가 **용어집과 `DS-nn` 에 반영**됐는가 |
| `design/screens/*/template/**` | **JS 가 남아 있지 않은가** ／ 4상태 4파일인가 ／ `SOURCE.md` 가 있는가 ／ UI-SPEC 과 어긋나지 않는가 |
| `.github/**`·`scripts/**`·`.claude/**` | `GITHUB_TOKEN` 권한 최소화와 액션의 **SHA 고정** ／ CODEOWNERS 보호 범위 ／ 시크릿의 취급 ／ **AI에게 허용하는 조작이 바뀌지 않았는가** |

**R3·R4·R6**(애매어·140자·LLM 말투)은 훅이 본다.

다만 훅이 도는 것은 **AI가 Write·Edit 로 쓴 `.md`** 뿐이다. **Bash 경유·사람의 에디터로 들어온 차분과 PR 본문에는 이 스킬이 R3·R4·R6 도 적용한다.**

| 판정 조건 | 아크션 |
|---|---|
| 차분이 코드 변경을 포함한다 | `/code-review` 를 함께 쓰고, 그 결과에 위 표의 관점을 얹는다 |
| 차분이 문서뿐이다 | `/code-review` 를 **부르지 않는다**(코드 결함 중심의 관점이 헛돈다) |

### 5. 4단의 검사를 실행한다

**PR 본문이 근거로 든 사실은, 쓰여 있다는 이유로 정본으로 삼지 않는다.**

1. 차분과 PR 본문의 독해
2. **리포 안의 결정적 검사** — `python3 scripts/check-docs.py` ＋ `.claude/hooks/*.test.sh`. 이 리포에 빌드·테스트 하니스는 없다([ADR-0005](../../../docs/adr/0005-design-team-deliverables.md))
3. **외부 일차정보 조회** — 패키지 레지스트리·라이선스·상류 릴리스 노트 등, PR 본문이 근거로 든 것
4. **CI 실행 로그의 읽기** — 체크가 녹색이어도 검사가 돌지 않은(가짜 그린) 경우의 검출

**실행하지 않은 검사가 있으면 리뷰 본문에 그렇게 쓴다.** 돌린 척하지 않는다.

### 6. 재리뷰 — 기존 지적의 해소를 확인하고, 범위를 지난번 이후의 차분으로 좁힌다

**자기가 지난번에 준 근거가 틀렸으면 그것을 먼저 밝힌다.**

### 7. 본문을 만들고 승인을 얻어 올린다

**승인을 얻지 않고 올리지 않는다.**

## 끊는 판정 — 무엇을 지금 고치게 하고, 무엇을 보내는가

리뷰와 수정의 왕복은 **라운드 수로는 끝나지 않는다.** 매 라운드 새로 깊이 파면 지적은 계속 나온다. 끝은 **새 지적의 출처 × 되돌릴 수 없음**으로 정한다.

클래스는 5단이다. **1.계약·스키마의 형 2.보안·인가 3.코드·문서의 오류 4.기록의 어긋남 5.서식.**

| 판정 조건(**각 라운드**에 나온 지적) | 아크션 |
|---|---|
| **지난 지적의 수정이 들여온 것**(회귀·표 밖으로 나간 행·건수 어긋남·main 충돌) | **지금 고친다.** 방치하면 지난 지적이 미달로 끝난다 |
| **신규 발견**이고 **클래스 1~2** | **지금 고친다.** Ready 화와 머지를 막는다 |
| **신규 발견**이고 **클래스 3~5** | **첫 라운드부터 기본으로 후속으로 보내고 끊는다.** 기표자가 그 자리에서 고치는 것은 자유다 |
| **자기가 지난번에 준 근거의 오류**에 기인 | 오류를 밝힌 뒤, 취급은 위와 같다 |
| **4라운드째가 필요하다고 읽힌다** | **리뷰의 문제가 아니라 UI-SPEC의 문제로 다룬다.** PR을 닫고 UI-SPEC으로 되돌리는 판단을 **사람에게 낸다**(스스로 정하지 않는다) |

## 후속의 행선지 (보낸다면 반드시 쓴다)

**「끊는다」를 「잊는다」로 만들지 않는다.** 행선지 없는 보류는 지적을 버리는 것과 같다.

| 판정 조건 | 아크션 |
|---|---|
| 지적을 보낸다 | **「후속」 절에 1건 1행**으로 내용과 행선지를 쓴다 |
| 디자인 시스템에 부족한 것이다 | `design/DS-update-list.md` 에 `DS-nn` 으로 기표하도록 의뢰한다 |
| 2화면 이상에서 성립하는 UX 판단이다 | `design/UX-PATTERNS.md` 에 `P-nn` 으로 |
| 그 화면에서만 성립한다 | 그 화면의 `UI-SPEC.md` §6으로 |
| 사람의 재정이 필요하다 | **리뷰 본문에 선택지와 추천을 써서 디자이너에게 낸다.** 스스로 정하지 않는다 |
| **행선지가 정해지지 않는다** | **보내지 않는다.** 지금 고치게 하거나, 위의 「4라운드째」로 넘긴다 |

## 금지 사항

- **승인을 얻지 않고 올리는 것**
- **approve·merge·수정의 push 를 하는 것.** Review 상태를 사람 대신 고르는 것
- **구현한 세션에서 이 스킬을 돌리는 것**
- 돌리지 않은 검사를 돌린 것처럼 쓰는 것
